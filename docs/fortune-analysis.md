# 發牌占卜：舊版 `analyzeHand` 的比對結果

起因：要移植舊版的發牌占卜，先確認那 80 行特殊牌型偵測能不能照搬。

工具：`tools/diff-analyze.py` 把舊版的 `analyzeHand`（L3445，111 行）原封不動抽進沙箱，
只把它唯一的外部依賴 `findNeeded13` 換成 `rules-core` 的 `winningTiles`
（舊的那支有六對子 bug，用它會混進另一個已知問題）。

```bash
python3 tools/diff-analyze.py && node /tmp/mj-analyze-test.js
```

---

## 結論：大部分正確，但**九連寶燈的判定壞得很嚴重**

### 🐛 九連寶燈：97.9% 是誤判

舊版的判定（L3472 附近）：

```js
if(!specialHint && domCount>=11 && honors<=2 && otherCount<=2){
  const has1=nums.filter(n=>n===1).length, has9=nums.filter(n=>n===9).length;
  if(has1>=1 && has9>=1){
    specialHint='九連寶燈';        // ← 只要有一張 1 和一張 9
  } else {
    specialHint='清一色';
  }
}
```

**只要有一張 1 和一張 9 就喊九連寶燈。**
但九連寶燈是 `1112345678999` —— **三張 1、三張 9**。

實測（4,000 副清一色手牌）：

| | |
|---|---|
| 喊出九連寶燈 | 2,908 次 |
| 真的接近的（≥2 張 1、≥2 張 9，且 1–9 齊全） | 62 次 |
| **誤判** | **2,846 次（97.9%）** |

誤判例子：

```
1334566677899   只有 1 張 1、2 張 9
1135566678899   只有 2 張 1、2 張 9
```

**為什麼要在意**：占卜的提示是拿來**下注**的。玩家被告知「九連寶燈潛力」
而押了孤注一擲（×3），實際上那手離九連還有四張以上，等於被騙進高風險選項。

這個 bug 在隨機發牌時很少觸發（一萬副起手裡零次，因為 `domCount>=11` 本來就罕見），
但**一觸發就幾乎一定是錯的** —— 而且觸發的時機正好是玩家真的有清一色手牌、
最可能認真下注的時候。

## 其餘的判定：測過沒問題

| 測項 | 結果 |
|---|---|
| 差一張就成的特殊牌型，提示講不講得出來 | ✅ 大四喜／字一色／綠一色／國士無雙／小三元／七對子／對對胡／混一色 全中 |
| 雜牌會不會亂喊 | ✅ 不喊 |
| 優先序與 `SPECIAL_HANDS` 的分數順序 | ✅ 一致（大四喜 > 字一色、小三元 > 對對胡、七對子 > 對對胡） |
| 一萬副隨機起手的提示率 | 4.45%，分布合理 |

隨機起手的提示分布：

```
七對子   2.02%      混一色   1.21%      國士無雙 1.18%
小三元   0.03%      對對胡   0.01%
```

> 註：`對對胡` 與 `七對子` 的判定條件不可能同時成立
> （2 刻 + 4 對 = 14 張 > 13），所以兩者的先後順序不影響結果。

---

## 建議：重寫，不要照搬

三個理由：

1. **九連那段是錯的**，照搬等於把 97.9% 的誤判一起搬過來
2. **那 80 行跟 `SPECIAL_HANDS` 重複**。牌型的定義已經在 `rules-core.js`
   （10 種、資料驅動），再維護一份平行的偵測邏輯，改一邊忘另一邊是遲早的事
3. 舊版的閾值是**兩人局**調的。四人局共用一副牌山、鳴牌機會多三倍，
   「有機會做成」的門檻本來就該重估

作法：新開 `src/fortune.js`，對每個 `SPECIAL_HANDS` 的牌型寫一個
「還差幾張」的估計函式，取最近又分數高的來提示。
由 `SPECIAL_HANDS` 驅動，新增牌型不用改兩個地方。

⚠️ **不要手改 `rules-core.js`** —— 那支是 `tools/build-rules-core.py` 產生的。
占卜疊在新模組裡。
